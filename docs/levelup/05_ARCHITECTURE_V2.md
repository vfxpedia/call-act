## A. 듀얼 트랙 STT 아키텍처

### 현재 문제

현재 구조는 1.5초 VAD 청크를 **독립적으로** STT 처리합니다.
- 각 청크에 문맥이 없음 → 키워드 추출 품질 저하
- 매 청크마다 동일한 RAG 파이프라인 반복 → 중복 검색
- 전체 오디오에서는 잘 되는 STT가 짧은 청크에서는 품질 저하

### 제안: Track 1 (빠른 표시) + Track 2 (정확한 분석)

```
Track 1 (빠른 전사 - 화면 표시용):
  [1.5s 청크] → faster-whisper → 즉시 다이얼로그에 표시
  목적: "실시간으로 전사되고 있다"는 UX. 정확도는 부차적.

Track 2 (정확한 전사 - 키워드/RAG용):
  [누적 버퍼 5~10초] → 문맥 인식 스트리밍 ASR → 정확한 텍스트 → 키워드 → RAG
  목적: 문맥 기반으로 정확한 키워드 추출. 2~3초 지연 허용.
```

### 스트리밍 ASR vs 청크 독립 STT

```
청크 독립:  [청크1] → "카드"  [청크2] → "분실했"  [청크3] → "는데요"
            (매번 독립, 이전 결과 모름)

스트리밍:   [청크1] → "카드"
            [청크1+2] → "카드 분실했"  (이전 문맥 캐싱)
            [청크1+2+3] → "카드 분실했는데요"  (누적, lazy 교정)
```

스트리밍 ASR 후보:
- **VibeVoice Realtime 0.5B**: 이미 다운로드 완료, 스트리밍 + 화자분리 + 타임스탬프
- NVIDIA NeMo/Riva 스타일 접근: 캐싱 + 문맥 누적 + 예측

### 기술 검증 필요 항목

| # | 항목 | 방법 |
|---|------|------|
| 1 | VibeVoice Realtime 스트리밍 모드 API 확인 | 로컬 테스트 |
| 2 | partial result + final result 구조 검증 | API 문서 + 실험 |
| 3 | Track 1 + Track 2 동시 실행 시 GPU 메모리 | 프로파일링 |
| 4 | 1.5초 vs 3초 vs 5초 버퍼 비교 | WER + 체감 테스트 |

## B. 키워드-문서 캐시 + 4단계 응답 체계

### 핵심 아이디어

우리 문서 코퍼스는 유한하고 작음 (card_products 398 + service_guides 1,251 = **1,649건**).
자주 쓰이는 키워드 500~1,000개에 대한 keyword→document 매핑을 **서버 시작 시 미리 빌드**하면,
첫 키워드 감지 즉시 문서를 반환할 수 있음 (< 100ms, 벡터 검색 없이).

### 4단계 응답 체계

| 단계 | 시점 | 트리거 | 처리 방식 | 예시 |
|------|------|--------|-----------|------|
| **1** | < 1초 | Track 1 텍스트 | 화면에 텍스트 표시 | 실시간 전사 |
| **2** | 1~2초 | 첫 키워드 캐시 히트 | 역색인 조회 → 즉시 문서 | "나라사랑카드" → 상품 정보 |
| **3** | 3~5초 | Track 2 문맥 누적 | 캐시 문서 + LLM 가공 | "카드 비교" → 비교표 생성 |
| **4** | fallback | 캐시 미스 | 벡터 검색 + LLM | 예상 못한 질문 |

### 단계 3의 중요성 (KMS를 넘어서는 지능)

**키워드 트리거만으로는 Ctrl+F 검색(KMS)과 다를 바 없다.**
우리 시스템의 가치는 **의도 해석 + 동적 콘텐츠 생성**:

- "혜택 알려줘" → 정보 제공 (캐시 문서 그대로) = 단계 2
- "혜택 비교해줘" → LLM이 두 카드 데이터로 비교표 생성 = **단계 3**
- "이 카드 괜찮아요?" → 고객 이력 + LLM 추천 판단 = **단계 3**
- 완전 새로운 질문 → 벡터 검색 fallback = 단계 4

**캐시 = 속도 최적화 레이어, LLM = 지능 레이어.** 이 구분이 설계 원칙.

### 역색인 구조 (도메인 지식 그래프)

```
나라사랑카드
  ├── 관련 키워드: [군인, 병사, 국방부, 군부대]
  ├── 공통 액션: [발급, 재발급, 분실, 한도]
  ├── 관련 문서 (card_products): [doc_23, doc_24]
  └── 관련 가이드 (service_guides): [guide_401, guide_402, ...]

분실
  ├── 관련 키워드: [신고, 정지, 도난, 재발급, 긴급]
  ├── 관련 가이드: [guide_101, guide_102, ...]
  └── 조합 매핑:
       "나라사랑카드" + "분실" → [guide_401 분실 섹션, guide_101]
```

기존 FlashText (Phase B에서 구축)를 활용하여 O(1) 키워드 매칭 가능.
메모리: ~5MB (1,649 문서 역색인 전체).

### 설계 원칙

1. **캐시는 80%의 일반 케이스를 즉시 처리**, 나머지 20%는 벡터 검색이 담당
2. **다양성 보장**: 키워드 트리거만 맹신하지 않음. LLM 가공 레이어가 정보를 재구성
3. **역색인은 분석적으로 정교하게 설계**: DB 키워드 품질 (Data팀 D-3 분석) 기반
4. **문서 렌더링 포맷 표준화 선행**: 마크다운 테이블/리스트 등 화면 친화적 구조 필요

## C. 고객 이력 기반 지능형 응답

### 아이디어

LLM이 고객의 상담 히스토리를 참조하여 맥락 있는 응답을 제공:
- "이 카드 괜찮아요?" → 고객의 기존 카드, 사용 패턴, 최근 문의 기반 추천
- 반복 문의 감지 (7일 이내 동일 문의 → "지난번에 말씀하신 건으로...")
- 교육 시뮬레이션에서도 활용 (시나리오별 고객 히스토리 제공)

### 구현 고려사항

| 항목 | 내용 |
|------|------|
| 데이터 소스 | consultations 테이블 (customer_id 기반 조회) |
| 유효 기간 | 최근 30일 (7일 이내 = 높은 가중치, 1년+ = 무시) |
| 제공 형태 | LLM system prompt에 최근 N건 요약 삽입 |
| 시연 와우포인트 | 반복 문의 자동 감지 + 맞춤 추천 |

### 우선순위

현재는 설계 단계. **듀얼 트랙 STT + 키워드 캐시가 먼저 해결되어야 함.**
고객 이력은 그 기반 위에서 추가되는 지능 레이어.

## D. GPU 리소스 단계별 로딩

### 현재 할당

| 모드 | GPU 0 (16GB) | GPU 1 (16GB) |
|------|-------------|-------------|
| 교육 | kanana-2.1B (4G) + ASR (4.4G) | Qwen3-TTS (2.4G) |
| ACW | kanana-8B-AWQ (5.4G) | analysis-AWQ (5.4G) |
| 전체 | 2.1B + 8B-AWQ (~9.4G) | TTS + analysis (~7.8G) |

### 제안: 단계별 동적 로딩

**모든 모델을 동시에 올릴 필요 없음.** 상담 프로세스 단계에 따라 로드/언로드:

```
교육 모드:     GPU0 = 2.1B(4G)              GPU1 = TTS(2.4G)
상담 중:       GPU0 = faster-whisper(3G)     GPU1 = VibeVoice-RT(1.5G)
로딩 구간:     (모델 스왑 ~10초, 로딩 페이지가 이 시간을 커버)
후처리:        GPU0 = kanana-8B-AWQ(5.4G)   GPU1 = analysis-AWQ(5.4G)
```

### 11.7초 로딩 시간과의 연계

현재 로딩 페이지가 10초 + 0.8초 fade = ~11.7초를 확보:
- 이 시간 동안 모델 스왑 가능 (vLLM 모델 로드 ~5-8초)
- LLM 분석도 이 시간 안에 병렬 수행
- **로딩 페이지가 리소스 전환의 버퍼 역할을 이미 하고 있음**

다만 주의: 로딩 페이지 첫 화면 요소(요약, 피드백)는 빠르게 준비되어야 함.
→ 모델 스왑과 LLM 호출의 순서/병렬화 설계 필요.

## E. 모델 필요성 재검토

### 현재 ACW 실제 사용 현황 (코드 분석 결과)

| 모델 | 용도 | **실제 호출 시점** | 비고 |
|------|------|-------------------|------|
| GPT-4.1-mini (외부) | 요약 + 피드백 | 로딩 중 (asyncio.gather 병렬) | **메인 ACW 플로우** |
| kanana-8B-AWQ | 텍스트 교정 | **현재 미호출** | ACW에서 실제 안 쓰임 |
| kanana-analysis-AWQ | 성격 분류 | 저장 클릭 시만 | 메인 플로우 아님 |

**발견**: 후처리 핵심(요약+피드백)이 이미 **외부 API (GPT-4.1-mini)** 사용 중.
kanana-8B-AWQ는 ACW에서 실제로 호출되지 않는 상태.

### 재검토 대상

| 모델 | 질문 | 결론 방향 |
|------|------|-----------|
| kanana-8B-AWQ | STT가 충분히 정확하면 교정이 필요한가? | faster-whisper 91% + 교정사전으로 충분할 수 있음. 검증 필요 |
| kanana-analysis-AWQ | 성격 분류를 로컬 5.4GB 모델로 할 필요가 있나? | 후처리는 실시간 아님. 대안 검토 가능 |
| GPT-4.1-mini | 외부 API 의존 → 데이터 외부 유출 우려 | **kanana-8B를 요약+피드백용으로 전환하는 것이 1안** |

### 1안: kanana-8B로 외부 API 대체 (보안 강화)

```
현재:  요약 → GPT-4.1-mini (외부)    피드백 → GPT-4.1-mini (외부)
1안:   요약 → kanana-8B-AWQ (로컬)    피드백 → kanana-8B-AWQ (로컬)
```

장점: 데이터가 외부로 나가지 않음, GPU 활용도 높아짐
단점: 품질 검증 필요 (kanana-8B vs GPT-4.1-mini 한국어 상담 요약 품질)

### 검증 계획

kanana-8B-AWQ가 GPT-4.1-mini 수준의 요약/피드백을 생성하는지 비교 테스트 필요:
- 동일 transcript 10건 → 두 모델 출력 비교
- 평가 기준: 요약 정확도, 카테고리 분류 정확도, 피드백 품질

## 참고: 현재 로딩 페이지 타임라인

```
0ms ─── LoadingPage 표시, 프로그래스바 시작 (0→100% / 10초)
         Step 0: "상담 데이터 저장중..."
2.5s ── Step 1: "상담 내용 분석중..."
         Backend: Redis에서 전사 데이터 대기 + GPT-4.1-mini 병렬 호출
5.0s ── Step 2: "AI 요약본 생성중..."
7.5s ── Step 3: "문서 완성중..."
8-10s ─ LLM API 결과 도착 → localStorage 저장
10.0s ─ 프로그래스바 완료 → fade-out (0.8초)
10.8s ─ ACW 페이지로 이동
~12s ── 폼 필드 렌더링 완료 (타이프라이터 효과)
```

이 10초 버퍼가 모델 스왑 시간도 커버할 수 있는 핵심 구간.
