### 2.1 파일명 통일 문제 ✅ 해결

**문제**: 출력 파일명이 `tedicard_*.json`로 되어 있음

**해결**:

- 스크립트는 이미 올바르게 작성되어 있었음 (이전 실행 결과만 변경 필요)

**영향 범위**:
- `teddycard_service_guides_samsung.json`
- `teddycard_service_guides_hyundai.json`
- `teddycard_service_guides_shinhan.json`
- `teddycard_service_guides_special.json`
- `teddycard_notices.json`
- `teddycard_card_products.json`
- `teddycard_*_enriched.json` (모든 보강 파일)

### 2.2 created_by 필드 처리 ✅ 확인

**문제**: `notices` 테이블의 `created_by` 필드가 모두 `null`

**분석**:
- Frontend에서 EMP-NNN 형식 사번 사용 (예: EMP-002, EMP-034)
- `employees` 테이블은 존재하지만 공지사항과 직접 FK 관계 없음
- 원본 데이터에 작성자 정보가 없어서 `null`이 올바른 값

**결론**:
- 기존 데이터는 `null` 유지 (원본에 작성자 정보 없음)
- Frontend에서 null 처리 로직 필요:
  - 예: `created_by || "시스템"` 또는 `created_by || "-"`
- 향후 관리자 시스템에서 공지사항 작성 시 EMP-NNN 형식으로 저장

**ERD 확인**:
```sql
created_by varchar(50) [note: '작성자 ID']
-- NULL 가능 (기존 데이터)
```

### 2.3 special_card 데이터 전처리 ✅ 확인

**문제**: `content: "없음"`, `text: "연회비 없음"`, `keywords: []` 등 빈 값들

**분석**:
- 원본 데이터: `special_terms.json`에서 `content: "없음"` 형태로 저장됨
- 이는 원본 데이터의 특성 (연회비 정보가 실제로 없음)
- `keywords`는 아직 추출되지 않았음 (키워드 추출 스크립트 실행 필요)

**결론**:
- `content: "없음"`은 원본 데이터가 올바름 (연회비가 실제로 없는 카드)
- `keywords: []`는 키워드 추출 스크립트 실행 후 채워짐
- 전처리 로직 자체는 정상 작동

**데이터 출처 확인**:
- `data-preprocessing/parsing/special_card/` 스크립트로 생성
- 원본 MD 파일(`국민행복(신용_체크).md`)을 기반으로 파싱됨
- `special_terms.json`, `special_faq.json` 구조 확인 완료

---

### 2.4 category1 vs category2 구조 ✅ 확인

**현재 구조**:
- ERD: `service_guide_documents.category varchar(100)` (단일 카테고리)
- 전처리: `category`에 category1 저장, `metadata`에 original_category1/category2 보존

**분석**:
- **RAG 검색 관점**: 단일 category로 충분 (임베딩이 의미적 유사도 처리)
- **Frontend 필터링 관점**: metadata에 category1/category2 보존하면 유연성 확보
- **원본 데이터**:
  - 삼성/현대/신한: category1/category2 구조
  - special_card: 단일 category 구조

**결론**: 현재 구조 유지
- `category` 필드는 DB 검색/필터링용 (단일 값)
- `metadata.original_category1`, `metadata.original_category2`는 원본 구조 보존
- Frontend에서 필요 시 metadata 활용 가능

---

### 2.5 keywords 필드 비어있음 ✅ 해결

**문제**: 모든 문서의 `keywords: []`

**해결**: 키워드 추출 스크립트 구현 완료

**구현 내용**:
1. 단어사전 구축 (`keywords_dict.json`)
   - 14개 카테고리, 총 100+ 키워드
   - 카드종류, 결제, 포인트, 분실도난, 연체, 혜택, 본인확인, 해외, 대출, 연회비, 신용도, 가맹점, 모바일 등

2. 키워드 추출 스크립트 (`08_extract_keywords.py`)
   - 단어사전 기반 키워드 매칭 (필수)
   - LLM 기반 키워드 추출 (선택적 보완)
   - 하이브리드 전략: 단어사전 + LLM

**사용법**:
```bash
# 단어사전만 사용 (빠름)
python 08_extract_keywords.py

# LLM 보완 포함 (더 정확하지만 느림)
python 08_extract_keywords.py --use-llm
```

**STT와의 연계**:
- 단어사전을 STT 키워드 추출에도 활용
- RAG 검색 시 키워드 기반 필터링 가능
- 하이브리드 전략으로 검색 정밀도 향상

---

### 2.6 content vs text 필드 ✅ 확인

**현재 구조**:
- `content`: 개행 포함 (Frontend 표시용)
- `text`: 개행 제거 (임베딩 생성용)

**분석**:
- 일부 문서에서 content와 text가 동일한 것은 정상
- 원본 데이터가 이미 개행 없이 저장된 경우

**결론**: 현재 구조가 올바름
- `content`: 포맷팅 보존 (개행, 구조)
- `text`: 의미 단위로 처리 (개행 제거하여 임베딩 품질 향상)

---

### 2.7 merge 로직 일관성 ✅ 검토 및 조정

**현재 상태**:
- 삼성: `merge_by_category2` 적용 (개별 객체 제거, merge된 객체만 저장)
- 현대: merge 미적용
- 신한: merge 미적용

**merge 대상 확인 결과**:

1. **현대 데이터**:
   - merge 후 68건 감소 (128건 → 60건)
   - merge 그룹 21개
   - 예: "Apple Pay 이용처" 관련 21개 문서 → 1개로 통합
   - **결론**: merge 적용 권장 ✅

2. **신한 데이터**:
   - merge 후 951건 감소 (988건 → 37건)
   - 문제: "본문" 카테고리가 634건
   - 약관 문서는 조(條) 단위로 분할되어 있음
   - 각 조가 "본문" 카테고리로 분류됨
   - **결론**: merge 적용 비권장 ❌
     - 약관은 조 단위 검색이 더 정확함
     - 통합 시 검색 정확도 하락 우려

**조치**:
- 현대 데이터에 merge 로직 적용 완료
- 신한 데이터는 merge 미적용 유지 (원본 구조 유지)

**merge 기준**:
- `metadata.original_category2` 동일한 문서들을 통합
- 통합된 문서는 `metadata.merged_from`에 원본 ID 목록 보존
- 통합된 문서는 `metadata.is_merged: true`로 표시

---

### 2.8 merge 결과 확인 ✅ 확인

**삼성 merge 예시**:
- 원본: `소비자가이드_1` ~ `소비자가이드_10` (10개)
- merge 후: `신용도 관리방법_merged` (1개)
- `metadata.merged_from`: 원본 ID 목록 보존

**장점**:
- RAG 검색 시 더 풍부한 컨텍스트 제공
- 관련 정보를 한 번에 검색 가능

**단점**:
- 개별 문서 검색 불가
- 하지만 `merged_from`으로 원본 문서 추적 가능

**결론**: merge 로직이 올바르게 작동함

## 3. 추가 확인 사항

### 3.1 special_card 데이터 구조

**원본 데이터 구조**:
- `metadata.category`: 단일 카테고리 (category1/category2 구조 없음)
- `metadata.card_name`: 카드명 (예: "국민행복카드", "K패스")

**전처리 결과**:
- `category`: 원본 category 그대로 저장
- `metadata.original_category`: 원본 category 보존
- **결론**: 원본 구조가 단일 카테고리이므로 현재 구조가 올바름

### 3.2 ID 필드에 "SHINHAN", "신한카드" 남아있음

**분석**:
- ID는 식별자이므로 변경하지 않는 것이 맞음
- 예: `CARD-SHINHAN-{card_name}` → 데이터 출처 추적 가능
- `name` 필드에는 "테디카드"로 치환되어 있음

**결론**: ID는 변경하지 않음 (정상)
