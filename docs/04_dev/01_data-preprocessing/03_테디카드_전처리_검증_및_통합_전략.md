## 3. 서비스 가이드 분리 이유

### 3.1 중간 단계 파일 분리

전처리 과정에서 각 데이터 소스별로 파일을 분리한 이유:

1. **처리 편의성**: 각 데이터 소스별로 변환 및 검증 용이
2. **디버깅 용이성**: 특정 데이터 소스의 문제를 빠르게 식별
3. **점진적 처리**: 각 데이터 소스를 단계적으로 처리 가능

### 3.2 최종 통합

`06_generate_embeddings.py`의 `merge_and_save_outputs()` 함수에서 모든 파일을 통합:

```python
# service_guide_documents 파일들 통합
service_guide_files = [
    INPUT_DIR / "tedicard_service_guides_hyundai.json",
    INPUT_DIR / "tedicard_service_guides_samsung.json",
    INPUT_DIR / "tedicard_service_guides_shinhan.json",
    INPUT_DIR / "tedicard_service_guides_special.json",
]

all_service_guides = []
for file_path in service_guide_files:
    if file_path.exists():
        data = load_json_file(file_path)
        all_service_guides.extend(data)  # 모든 파일을 하나로 통합

# 최종적으로 하나의 파일로 저장
output_file = OUTPUT_DIR / "tedicard_service_guides_with_embeddings.json"
```

**결론**: 중간 단계는 분리하되, 최종 결과는 계획 문서의 "옵션 B: 통합 구조"에 따라 하나로 통합됩니다.

## 4. 문서 통합 전략 (Category2 기준 통합)

### 4.1 문제 상황

원본 데이터에서 "신용도 관리방법" 같은 카테고리가 여러 개의 별도 문서로 분리되어 있습니다:

1. "본인의 개인신용평점에 관심을 기울이세요"
2. "연체가 발생하지 않도록 유의하세요"
3. "주소가 변경된 경우 금융회사 등에 반드시 통보하세요"
4. "카드대금 결제 등은 자동이체를 활용하세요"
5. "대부업체의 신용정보 조회..."
6. "신용카드 단기카드대출(현금서비스) 이용..."
7. "빈번하거나 과도한 대출을 자제하세요"
8. "정상적인 신용 거래는 개인신용평점에 긍정적으로 작용합니다"
9. "주거래 금융회사를 정해 거래실적을 유지·관리하세요"
10. "장기간에 걸친 지속적인 신용관리가 필요합니다"

### 4.2 RAG 검색 효율성 분석

#### 현재 방식 (10개 객체로 분리)

**장점**:
- 각 항목이 독립적이고 명확함
- 특정 키워드(예: "연체")로 정확한 문서 검색 가능
- 문서 크기가 작아 임베딩 품질이 안정적

**단점**:
- "신용도 관리방법" 관련 쿼리 시 일부만 검색될 수 있음
- 관련 정보를 모두 전달하려면 여러 문서를 조합해야 함

#### 통합 방식 (1개 객체로 합치기)

**장점**:
- "신용도 관리방법" 관련 쿼리 시 한 문서에서 관련 정보를 모두 제공
- 컨텍스트가 풍부하여 LLM이 더 나은 답변 생성 가능

**단점**:
- 문서가 길어지면 임베딩 품질 저하 가능
- 특정 항목(예: "연체")만 필요한 경우 불필요한 정보 포함

### 4.3 하이브리드 접근법

**전략**: Category2 기준으로 그룹화하여 통합

1. **같은 category2를 가진 문서들을 하나로 통합**
2. **RAG 검색**: 통합된 문서에서 검색 (전체 컨텍스트 제공)
3. **LLM 요약**: 검색된 문서를 LLM이 요약하여 전달
4. **Keywords 기반 필터링**: 이후 로직에서는 keywords에 맞춰서 정확한 정보 전달

**구현 방법**:
- `merge_by_category2()` 함수 추가
- 같은 `metadata.original_category2` 값을 가진 문서들을 하나로 통합
- 통합된 문서의 `metadata.merged_from`에 원본 문서 ID 목록 저장

## 5. 구현 세부사항

### 5.1 통합 로직

```python
def merge_by_category2(documents: List[Dict]) -> List[Dict]:
    """
    같은 category2를 가진 문서들을 하나로 통합
    
    Args:
        documents: 문서 리스트
    
    Returns:
        통합된 문서 리스트
    """
    from collections import defaultdict
    
    grouped = defaultdict(list)
    for doc in documents:
        category2 = doc.get('metadata', {}).get('original_category2', '')
        if category2:
            grouped[category2].append(doc)
    
    merged_docs = []
    standalone_docs = []
    
    for category2, docs in grouped.items():
        if len(docs) > 1:  # 여러 개일 때만 통합
            # 첫 번째 문서를 기준으로 통합
            merged = docs[0].copy()
            merged['id'] = f"{category2}_merged"
            merged['title'] = category2  # 카테고리 이름을 제목으로
            merged['content'] = '\n\n'.join([d['content'] for d in docs])
            merged['text'] = '\n\n'.join([d['text'] for d in docs])
            merged['metadata']['merged_from'] = [d['id'] for d in docs]
            merged['metadata']['is_merged'] = True
            merged_docs.append(merged)
        else:
            standalone_docs.extend(docs)
    
    return merged_docs + standalone_docs
```

### 5.2 적용 범위

**통합 대상**:
- 같은 `metadata.original_category2` 값을 가진 문서가 2개 이상인 경우
- 예: "신용도 관리방법" (10개 문서 → 1개로 통합)

**통합 제외**:
- `original_category2` 값이 없는 경우
- 같은 category2를 가진 문서가 1개인 경우

### 5.3 메타데이터 구조

통합된 문서의 메타데이터 구조:

```json
{
  "id": "신용도 관리방법_merged",
  "title": "신용도 관리방법",
  "content": "... (10개 문서의 내용 통합) ...",
  "text": "... (10개 문서의 텍스트 통합) ...",
  "metadata": {
    "original_source": "samsung",
    "original_category1": "신용카드",
    "original_category2": "신용도 관리방법",
    "merged_from": [
      "소비자가이드_1",
      "소비자가이드_2",
      "소비자가이드_3",
      ...
    ],
    "is_merged": true,
    "preprocessing_date": "2026-01-11",
    "preprocessing_version": "1.0"
  }
}
```

## 6. RAG 검색 워크플로우

### 6.1 검색 단계

1. **고객 쿼리**: "신용도 관리방법이 뭐예요?"
2. **임베딩 검색**: 통합된 "신용도 관리방법" 문서 검색
3. **문서 반환**: 통합된 문서 (10개 항목 포함)

### 6.2 LLM 요약 단계

1. **검색된 문서**: 통합된 "신용도 관리방법" 문서
2. **LLM 요약**: 전체 내용을 요약하여 전달
3. **답변 생성**: "신용도 관리방법은 다음과 같습니다: 1) 개인신용평점 확인, 2) 연체 방지, 3) 주소 변경 시 통보, ..."

### 6.3 Keywords 기반 필터링 (향후 구현)

1. **고객 쿼리**: "연체하면 어떻게 되나요?"
2. **임베딩 검색**: 통합된 "신용도 관리방법" 문서 검색
3. **Keywords 필터링**: "연체" 키워드가 포함된 부분만 추출
4. **정확한 정보 전달**: "연체가 발생하지 않도록 유의하세요..." 부분만 전달

## 7. 장단점 분석

### 7.1 통합 방식의 장점

1. **RAG 검색 효율성 향상**: 관련 정보를 한 번에 검색
2. **컨텍스트 풍부성**: LLM이 더 나은 답변 생성 가능
3. **정보 완전성**: 관련 정보를 모두 포함하여 누락 방지

### 7.2 통합 방식의 단점 및 대응

1. **문서 크기 증가**
   - **대응**: 임베딩 최적 길이(200~800 토큰) 확인 필요
   - **대응**: 필요 시 청킹(chunking) 전략 적용

2. **특정 항목 검색 시 불필요한 정보 포함**
   - **대응**: Keywords 기반 필터링 로직 추가
   - **대응**: LLM이 요약 시 관련 부분만 추출하도록 프롬프트 설계

3. **임베딩 품질 저하 가능성**
   - **대응**: 통합 후 임베딩 품질 테스트 필요
   - **대응**: 필요 시 분리 방식과 통합 방식의 하이브리드 적용
