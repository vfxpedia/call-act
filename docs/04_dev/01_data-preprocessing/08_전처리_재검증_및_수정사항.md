## 1. 발견된 문제점

### 1.1 notices 날짜 불일치 문제

**문제**: 
- 원본 데이터: `"date": "2025.10.20"`
- Content 내용: "2025년 9월 26일, 국가정보자원관리원 화재로 인한..."
- 보강 결과: `start_date: "2025-10-20"`

**분석**:
- 원본 데이터의 `date` 필드는 **공지사항이 게시된 날짜**를 의미합니다.
- Content 내의 "2025년 9월 26일"은 **사건이 발생한 날짜**를 의미합니다.
- 따라서 `start_date`는 공지사항 게시일(`date`)을 사용하는 것이 맞습니다.

**결론**: 현재 로직이 올바릅니다. 다만, 향후 content에서 사건 발생일을 추출하여 별도 필드(`event_date`)로 저장하는 것을 고려할 수 있습니다.

---

### 1.2 end_date 계산 로직

**현재 로직**:
```python
if priority == "urgent":
    return start_date + timedelta(days=7)  # 긴급: 1주일
elif priority == "important":
    return start_date + timedelta(days=14)  # 중요: 2주일
else:
    return start_date + timedelta(days=14)  # 일반: 2주일
```

**문제**: 
- 모든 공지사항이 무조건 2주가 아닌지 확인 필요
- Content에서 종료일 정보를 추출할 수 있는지 확인 필요

**개선 방안**:
1. Content에서 "~까지", "~일까지", "종료일" 등의 키워드로 종료일 추출 시도
2. 추출 실패 시 priority 기반 기본값 사용
3. 긴급 공지는 1주일, 중요/일반은 2주일 (현재 로직 유지)

---

### 1.3 created_by 필드

**ERD 정의**:
```dbml
created_by varchar(50) [note: '작성자 ID']
```

**현재 값**: `null`

**설명**:
- `created_by`는 공지사항을 작성한 사람의 ID입니다.
- 원본 데이터(삼성카드 공지사항)에는 작성자 정보가 없습니다.
- 따라서 `null`이 맞습니다.
- 향후 관리자 시스템에서 공지사항을 작성할 때 `created_by`를 설정할 수 있습니다.

**결론**: 현재 값(`null`)이 올바릅니다.

### 1.4 card_products ID에 "SHINHAN", "신한카드" 남아있음

**예시**:
- `"id": "CARD-SHINHAN-11번가-팝-신한카드-체크"`
- `"id": "CARD-SHINHAN-(이응패스-여민전)-K-패스-체크"`

**분석**:
- ID는 **식별자(identifier)**이므로 변경하지 않는 것이 맞습니다.
- ID를 변경하면:
  - 기존 데이터와의 연결이 끊어짐
  - 외부 시스템 참조 시 문제 발생
  - 데이터 추적 불가능

**결론**: ID는 그대로 유지하는 것이 올바릅니다. 다만, `name` 필드는 "테디카드"로 치환되어 있으므로 사용자에게는 올바르게 표시됩니다.

### 1.5 연회비가 모두 null

**현재 상태**:
```json
"annual_fee_domestic": null,
"annual_fee_global": null
```

**원인 분석**:
1. `01_convert_shinhan_cards.py`에서 연회비 파싱이 제대로 되지 않았을 수 있음
2. `07_enrich_for_db.py`의 `parse_annual_fee` 함수가 제대로 작동하지 않았을 수 있음

**확인 필요**:
- 원본 MD 파일에서 연회비 정보가 어떻게 저장되어 있는지
- 파싱 로직이 올바른지

**개선 방안**:
- `full_content`에서 연회비 테이블을 더 정교하게 파싱
- 정규표현식 패턴 개선
- 파싱 실패 시 로그 출력하여 수동 확인

### 1.6 full_content 중복

**현재 구조**:
```json
{
  "main_benefits": "...",  // 일부 내용만 포함
  "full_content": "...",   // 전체 내용
  "metadata": {
    "full_content": "..."  // 전체 내용 (중복)
  }
}
```

**분석**:
- `main_benefits`: 카드의 주요 혜택 요약 (간략)
- `full_content` (최상위): 전체 카드 정보 (임베딩 생성용)
- `metadata.full_content`: 백업용 전체 내용 (DB에는 저장하지 않음)

**차이점**:
- `main_benefits`: 요약된 정보 (RAG 검색 시 사용)
- `full_content`: 전체 정보 (임베딩 생성 및 상세 조회용)
- `metadata.full_content`: 원본 보존용 (DB 적재 시 제외)

**결론**: 
- `main_benefits`와 `full_content`는 다른 용도이므로 중복이 아닙니다.
- `metadata.full_content`는 중복이지만, 원본 보존을 위해 유지하는 것이 좋습니다.
- DB 적재 시 `metadata.full_content`는 제외하면 됩니다.

---

### 1.7 brand가 null

**현재 상태**:
- 일부 카드는 `"brand": "local"` 또는 `"brand": "visa"`로 정상 추출됨
- 일부 카드는 `"brand": null`

**원인 분석**:
- `extract_brand` 함수가 `full_content`에서 "Local", "VISA", "Mastercard" 등을 찾음
- 일부 카드의 `full_content`에 브랜드 정보가 명시되지 않았을 수 있음

**개선 방안**:
1. 원본 MD 파일의 테이블에서 브랜드 정보 추출 강화
2. `01_convert_shinhan_cards.py`에서 브랜드 파싱 개선
3. `full_content`에서 브랜드 추출 로직 개선
