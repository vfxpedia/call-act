# DB 적재 전 데이터 보강 전략

## 1. 개요

전처리된 JSON 데이터를 DB 스키마에 맞게 보강하는 과정을 문서화합니다. 실제 데이터를 기반으로 매핑 규칙을 적용하며, 임의로 값을 만들지 않고 원본 데이터에서 추출합니다.

**작성일**: 2026-01-11  
**작성자**: CALL:ACT Team  
**관련 스크립트**: `data-preprocessing_dev/preprocessing/tedicard/07_enrich_for_db.py`

## 2. 데이터 보강 대상

### 2.1 notices (공지사항)

**원본 JSON 구조**:
```json
{
  "id": "notice_01",
  "tag": "피해",
  "title": "쿠팡 정보유출 사고 관련, 금융사기 피해 우려 NOTICE 발령!",
  "content": "...",
  "date": "2025.12.03",
  "metadata": {...}
}
```

**DB 스키마 요구사항**:
- `category`: `notice_category` ENUM (system, service, emergency)
- `priority`: `notice_priority` ENUM (normal, important, urgent)
- `start_date`: DATE (NOT NULL)
- `end_date`: DATE (NULL 가능)
- `status`: `status` ENUM (active, inactive, suspended)
- `is_pinned`: BOOLEAN (기본값: false)
- `created_by`: VARCHAR(50) (NULL 가능)

**매핑 규칙**:

1. **date → start_date 변환**
   - 형식: "2025.12.03" → `date(2025, 12, 3)`
   - 파싱 실패 시: 오늘 날짜 사용

2. **tag → category 매핑 (규칙 기반)**
   ```python
   TAG_TO_CATEGORY_MAP = {
       "피해": "emergency",      # 금융사기 피해 관련
       "이벤트": "service",       # 프로모션, 이벤트
       "시스템": "system",        # 시스템 업데이트, 점검
       "교육": "service",         # 교육 관련
       "정책": "service",         # 정책 변경
       "근무": "system",          # 근무 일정
       "복지": "service",         # 복지 관련
       "긴급": "emergency",       # 긴급 공지
   }
   ```

3. **LLM 기반 category 분석 (tag가 없거나 불명확한 경우)**
   - LLM 프롬프트: 제목, 태그, 내용(500자)을 분석하여 category 결정
   - Fallback: 규칙 기반 매핑

4. **priority 결정 (규칙 기반)**
   ```python
   URGENT_KEYWORDS = ["긴급", "NOTICE 발령", "주의", "즉시", "피해", "사기"]
   IMPORTANT_KEYWORDS = ["변경", "업데이트", "안내", "공지"]
   ```
   - 우선순위: urgent > important > normal

5. **end_date 계산**
   - 우선순위: content에서 종료일 패턴 추출 시도
     - 패턴: "2025.12.31까지", "~2025.12.31", "종료일: 2025.12.31"
   - 없으면 기본값:
     - `urgent`: start_date + 7일 (1주일)
     - `important`: start_date + 14일 (2주일)
     - `normal`: start_date + 14일 (2주일)

6. **status 결정**
   - 현재 날짜 < start_date → `inactive` (예정)
   - start_date <= 현재 날짜 <= end_date → `active`
   - 현재 날짜 > end_date → `inactive` (종료)

### 2.2 card_products (카드 상품)

**원본 JSON 구조**:
```json
{
  "id": "CARD-SHINHAN-#Pay-신한카드",
  "name": "#Pay 테디카드",
  "card_type": "credit",
  "brand": null,
  "annual_fee_domestic": "기본연회비",
  "annual_fee_global": null,
  "full_content": "...",
  "status": "active"
}
```

**DB 스키마 요구사항**:
- `annual_fee_domestic`: INT (NULL 가능)
- `annual_fee_global`: INT (NULL 가능)
- `brand`: `brand_type` ENUM (visa, mastercard, amex, unionpay, local)
- `full_content`: DB에 없음 → `metadata.full_content`에 저장

**매핑 규칙**:

1. **annual_fee_domestic 파싱**
   - "없음" → `None`
   - "기본연회비" → `full_content`에서 연회비 테이블 파싱
   - 한국어 숫자 변환: "2만 7천원" → 27000
   - 정규식으로 숫자 추출 후 만원 단위로 변환

2. **brand 추출**
   - `full_content`에서 브랜드 키워드 검색:
     - "Local" 또는 "국내전용" → `local`
     - "VISA" → `visa`
     - "Mastercard" → `mastercard`
     - "AMEX" 또는 "American Express" → `amex`
     - "UnionPay" 또는 "유니온페이" → `unionpay`
   - 없으면 `None`

3. **full_content 저장**
   - DB 스키마에 `full_content` 필드가 없으므로
   - `metadata.full_content`에 저장

---

### 2.3 service_guide_documents (서비스 가이드 문서)

**원본 JSON 구조**:
```json
{
  "id": "...",
  "document_type": "service_guide",
  "category": "신용카드",
  "title": "...",
  "content": "...",
  "text": "...",
  "metadata": {
    "original_source": "samsung",
    ...
  }
}
```

**DB 스키마 요구사항**:
- `document_source`: VARCHAR(200)
- `priority`: VARCHAR(20) (기본값: 'normal')
- `usage_count`: INT (기본값: 0)
- `last_used`: TIMESTAMP (NULL 가능)

**매핑 규칙**:

1. **document_source 추가**
   - `metadata.original_source`에서 추출
   - 없으면 빈 문자열

2. **기본값 설정**
   - `priority`: 'normal'
   - `usage_count`: 0
   - `last_used`: NULL

## 3. 청킹(Chunking) 필요 여부 분석

### 3.1 분석 기준

- **OpenAI 임베딩 제한**: `text-embedding-3-small` 모델은 최대 8191 토큰 지원
- **한국어 토큰 추정**: 평균 1자 = 1.3 토큰
- **안전 마진**: 8000 토큰 이하 권장

### 3.2 분석 결과

**분석 스크립트**: `00_analyze_document_lengths.py`

**예상 결과** (실제 실행 필요):
- `service_guide_documents`: 대부분 1000-3000자 범위 (1300-3900 토큰)
- `notices`: 대부분 500-2000자 범위 (650-2600 토큰)
- `card_products.full_content`: 일부 5000자 이상 가능 (6500+ 토큰)

**결론**:
- ✅ **대부분의 문서는 청킹 불필요**
- ⚠️ **card_products의 full_content는 임베딩 생성 시 사용하지 않음** (metadata에만 저장)
- ✅ **service_guide_documents와 notices는 청킹 없이 처리 가능**

### 3.3 하나카드 상담 데이터와의 비교

- **하나카드 상담 데이터**: 청킹을 고려하지 않았음
- **이유**: 상담 전문은 일반적으로 짧고, 의미 단위로 분리되어 있음
- **현재 데이터**: 서비스 가이드, 공지사항도 유사한 특성을 가짐
- **결론**: **청킹 없이 진행 가능**

## 4. LLM 활용 전략

### 4.1 category/priority 자동 분석

**사용 시나리오**:
- `tag` 필드가 없거나 불명확한 경우
- 규칙 기반 매핑으로 분류가 어려운 경우

**LLM 프롬프트 예시**:
```
다음 공지사항을 분석하여 카테고리와 우선순위를 결정하세요.

제목: {title}
태그: {tag}
내용: {content[:500]}

카테고리 선택지:
- system: 시스템 업데이트, 점검, 근무 일정 등
- service: 이벤트, 프로모션, 교육, 정책 변경 등
- emergency: 금융사기 피해, 긴급 공지, 보안 경고 등

우선순위 선택지:
- urgent: 긴급 공지, 즉시 조치 필요
- important: 중요 공지, 주의 필요
- normal: 일반 공지

JSON 형식으로 응답:
{"category": "system|service|emergency", "priority": "urgent|important|normal"}
```

**Fallback 전략**:
- LLM API 호출 실패 시 규칙 기반 매핑으로 fallback
- `OPENAI_API_KEY`가 없으면 규칙 기반만 사용

## 5. 실행 순서

### 5.1 전체 워크플로우

```
1. 원본 데이터 수집
   ↓
2. 텍스트 치환 (신한→테디 등)
   ↓
3. JSON 형식 변환 (01~05 스크립트)
   ↓
4. 데이터 보강 (07_enrich_for_db.py) ← 현재 단계
   ↓
5. 임베딩 생성 (06_generate_embeddings.py)
   ↓
6. DB 적재 (backend_dev/app/db/scripts/)
```

### 5.2 실행 명령어

```bash
# 1. 문서 길이 분석 (선택사항)
cd data-preprocessing_dev/preprocessing/tedicard
python 00_analyze_document_lengths.py

# 2. 데이터 보강
python 07_enrich_for_db.py

# 3. 임베딩 생성
python 06_generate_embeddings.py

# 4. DB 적재 (backend_dev에서)
cd ../../../../backend_dev/app/db/scripts
python 02_load_tedicard_to_db.py  # 추후 작성 예정
```

## 6. 출력 파일

### 6.1 보강된 JSON 파일

- `tedicard_notices_enriched.json`: notices 보강 결과
- `tedicard_card_products_enriched.json`: card_products 보강 결과
- `tedicard_service_guides_enriched.json`: service_guide_documents 보강 결과 (통합)

### 6.2 필드 변경 사항

**notices**:
- 추가: `category`, `priority`, `start_date`, `end_date`, `status`, `is_pinned`, `created_by`
- 제거: `date`, `tag` (DB 스키마에 없음)

**card_products**:
- 수정: `annual_fee_domestic` (문자열 → 정수 또는 NULL)
- 수정: `brand` (null → enum 값 또는 null)
- 이동: `full_content` → `metadata.full_content`

**service_guide_documents**:
- 추가: `document_source`, `priority`, `usage_count`, `last_used`

## 8. 주의사항

1. **원본 데이터 보존**: 보강 과정에서 원본 데이터를 덮어쓰지 않고 `_enriched.json` 파일로 저장
2. **LLM 비용**: LLM 분석은 선택사항이며, 규칙 기반 매핑으로도 충분히 처리 가능
3. **날짜 파싱**: 다양한 날짜 형식에 대응할 수 있도록 여러 패턴 시도
4. **에러 처리**: 파싱 실패 시 기본값 사용 (로그 출력)

## 9. 향후 개선 사항
