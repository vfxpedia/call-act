## 1. 하나카드 데이터 처리 성능 분석

### 1.1 현재 처리 방식

**처리 대상**: 6,533건의 하나카드 상담 데이터

**실제 처리 데이터**:
- ✅ `metadata.keywords` 필드만 읽음 (각 문서당 평균 5-10개 키워드)
- ❌ `content` 필드는 읽지 않음 (각 문서당 평균 2,000-5,000자)
- ❌ `title` 필드는 읽지 않음

**메모리 사용량**:
- 하나카드 JSON 파일 크기: 약 50-100MB
- 실제 메모리 사용: JSON 로드 시 전체 파일 로드 필요 (약 100-200MB)
- 키워드 수집 후: 약 10-20MB (키워드만 저장)

**처리 시간 예상**:
- JSON 파일 로드: 5-10초
- 키워드 수집 (6,533건): 10-20초
- 빈도 계산 및 정렬: 5-10초
- **총 예상 시간: 20-40초**

## 2. 빈도수 융합 성능 분석

### 2.1 현재 처리 방식

**처리 단계**:
1. 카테고리별 키워드 수집: `O(n)` (n = 문서 수)
2. Counter로 빈도 계산: `O(m)` (m = 키워드 수)
3. 상위 50개 추출: `O(m log m)` → `O(50)` (most_common 최적화)
4. 병합: `O(k)` (k = 카테고리 수)

**예상 시간**:
- 키워드 수집: 10-20초
- 빈도 계산: 1-2초
- 상위 추출: 0.5-1초
- 병합: 0.5-1초
- **총 예상 시간: 12-24초**

### 2.2 최적화 여지

현재 방식이 이미 최적화되어 있습니다:
- `Counter`는 C로 구현되어 매우 빠름
- `most_common(50)`은 힙 정렬로 최적화됨
- 병합은 단순 set 연산으로 빠름

**추가 최적화 불필요**: 현재 성능으로 충분

## 3. 전처리 단계 구조화 데이터 생성 검토

### 3.1 현재 접근 방식

**옵션 A: 전처리 단계에서 구조화** (현재 구현)
- 장점:
  - ✅ RAG 검색 시 즉시 사용 가능 (LLM 재구성 불필요)
  - ✅ 응답 시간 대폭 단축 (500ms → 50ms)
  - ✅ 일관된 구조 보장
  - ✅ DB 적재 시 구조화된 데이터 저장 가능
- 단점:
  - ⚠️ 전처리 시간 증가 (약 1-2시간)
  - ⚠️ 모든 문서에 대해 구조화 필요 (일부만 사용될 수도 있음)

**옵션 B: RAG 검색 후 LLM 재구성** (기존 방식)
- 장점:
  - ✅ 전처리 불필요
  - ✅ 실제 사용된 문서만 구조화
- 단점:
  - ❌ 첫 검색 시 느림 (500ms-2s)
  - ❌ LLM 호출 비용 증가
  - ❌ 일관성 부족 (매번 다른 결과 가능)

### 3.2 권장사항: 전처리 단계 구조화 (옵션 A)

**이유**:
1. **성능 향상**: RAG 검색 응답 시간 10배 단축
2. **비용 절감**: LLM 호출 횟수 감소 (검색 시마다 호출 → 1회만 호출)
3. **일관성**: 동일 문서에 대해 항상 동일한 구조 보장
4. **확장성**: DB에 구조화된 데이터 저장 시 향후 활용 용이

**투자 대비 효과**:
- 전처리 시간: 1-2시간 (1회)
- RAG 검색 시간 절감: 500ms → 50ms (매 검색마다)
- **ROI**: 매우 높음 (특히 빈번한 검색 시)

### 3.3 DB 적재 전략

**권장 방식**: 전처리 단계에서 구조화된 데이터를 DB에 적재

**장점**:
1. **즉시 사용 가능**: RAG 검색 결과를 바로 프론트엔드에 전달
2. **DB 쿼리 최적화**: 구조화된 필드로 인덱싱 가능
3. **일관성 보장**: 모든 문서가 동일한 구조로 저장

**구현 예시**:
```sql
-- service_guide_documents 테이블에 structured 필드 추가
ALTER TABLE service_guide_documents 
ADD COLUMN structured JSONB;

-- 인덱싱 (선택적)
CREATE INDEX idx_structured_title ON service_guide_documents 
USING GIN ((structured->>'title'));
```
