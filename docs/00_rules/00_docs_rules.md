# 문서화 규칙

## 메타데이터
- **작성일**: 2025-12-23
- **작성자**: Project Team
- **버전**: v1.0
- **상태**: 완료

## 목적
이 문서는 프로젝트의 모든 문서화 작업에 대한 표준 규칙을 정의합니다. 일관된 문서 구조와 명명 규칙을 통해 문서의 가독성과 유지보수성을 향상시키고, 팀원 및 AI 협업 도구(Claude Code)와의 효율적인 협업을 지원합니다.

## 폴더 구조

```
docs/
├── 00_rules/          # 문서화 규칙 및 가이드
├── 01_planning/       # 기획 및 요구사항 문서
├── 02_architecture/   # 시스템 설계 및 아키텍처
├── 03_api/           # API 명세 및 문서
├── 04_meeting/       # 회의록 및 논의 기록
├── 05_development/   # 개발 관련 문서
├── 06_deployment/    # 배포 및 운영 문서
└── 99_archive/       # 구버전 및 참고 문서
```

### 폴더 구조 원칙
- 카테고리별로 폴더를 분리하여 관리
- 폴더명은 `NN_카테고리명` 형식 사용 (NN은 두 자리 숫자)
- 필요에 따라 새로운 카테고리 폴더 추가 가능
- 사용하지 않는 폴더는 미리 만들지 않음 (최소한의 구조 유지)

## 파일명 규칙

### 형식
```
YYYYMMDD_NN_제목.md
```

### 구성 요소
- **YYYYMMDD**: 작성일 (예: 20231223)
- **NN**: 같은 날짜의 문서 순번 (01, 02, 03, ...)
- **제목**: 간결하고 명확한 한글/영문 제목
  - 공백 대신 언더스코어(`_`) 사용
  - 특수문자 사용 지양
  - 20자 이내 권장

### 예시
- `20231223_01_프로젝트_초기기획.md`
- `20231224_01_요구사항_정리.md`
- `20231224_02_기술스택_선정.md`
- `20231225_01_시스템_아키텍처_설계.md`

## 문서 템플릿

모든 문서는 다음 템플릿을 기본으로 작성합니다:

```markdown
# 문서 제목

## 메타데이터
- **작성일**: YYYY-MM-DD
- **작성자**: 이름
- **버전**: v1.0
- **상태**: 작성중 | 검토중 | 완료 | 보류 | 폐기
- **관련 문서**: [링크](../카테고리/파일명.md)

## 목적
이 문서가 작성된 이유와 목표를 명확히 기술

## 배경
문서 작성에 필요한 맥락과 배경 정보 제공

## 내용
문서의 주요 내용 작성
- 필요에 따라 하위 섹션 구성
- 코드, 다이어그램, 표 등 활용

## 결론 / 다음 단계
- 핵심 결론 요약
- 후속 작업이나 액션 아이템 명시
```

### 메타데이터 필드 설명

| 필드 | 설명 | 예시 |
|------|------|------|
| 작성일 | 문서 최초 작성일 | 2023-12-23 |
| 작성자 | 문서 작성자 이름 | 홍길동, Claude Code |
| 버전 | 문서 버전 (주요 변경 시 증가) | v1.0, v1.1, v2.0 |
| 상태 | 문서의 현재 상태 | 작성중, 검토중, 완료, 보류, 폐기 |
| 관련 문서 | 연관된 다른 문서 링크 | [기획서](../01_planning/20231223_01.md) |

## 작성 원칙

### 1. 문서화 기준
- 중요한 의사결정과 그 배경은 반드시 문서화
- 복잡한 로직이나 아키텍처 설계는 문서로 설명
- 프로젝트 진행 과정의 주요 마일스톤 기록
- 회의 내용 중 액션 아이템이 있는 경우 문서화

### 2. 상호 참조
- 관련 문서는 상대 경로로 링크
  - 같은 카테고리: `[제목](./파일명.md)`
  - 다른 카테고리: `[제목](../카테고리명/파일명.md)`
- 메타데이터의 "관련 문서" 필드 활용
- 문서 내에서도 관련 섹션 참조 가능

### 3. 버전 관리
- Git을 통한 버전 관리 (커밋 히스토리로 변경 이력 추적)
- 문서의 주요 변경 시 메타데이터의 버전 번호 업데이트
  - 내용 추가/수정: 마이너 버전 증가 (v1.0 → v1.1)
  - 구조 변경/전면 개편: 메이저 버전 증가 (v1.9 → v2.0)

### 4. 아카이빙
- 더 이상 사용하지 않는 문서는 상태를 "폐기"로 변경
- 필요시 `99_archive/` 폴더로 이동
- 아카이브 시 원본 위치에 이동 정보 남기기:
  ```markdown
  # 구문서 제목

  **이 문서는 폐기되었습니다.**
  - 새 문서: [링크](../카테고리/새파일.md)
  - 아카이브 날짜: YYYY-MM-DD
  ```

### 5. 작성 스타일
- 명확하고 간결한 문장 사용
- 기술 용어는 처음 사용 시 설명 추가
- 필요한 경우 다이어그램, 표, 코드 예시 활용
- 마크다운 문법 준수 (Github-flavored Markdown)

## 새 카테고리 추가 방법

1. 적절한 번호와 이름으로 폴더 생성 (예: `07_testing/`)
2. 이 문서의 "카테고리 가이드" 섹션에 새 카테고리 설명 추가
3. 첫 문서 작성 시 파일명 규칙 준수

## 문서 작성 워크플로우

1. **문서 작성 전**
   - 적절한 카테고리 폴더 확인/생성
   - 파일명 규칙에 따라 파일 생성

2. **작성 중**
   - 템플릿 구조 사용
   - 메타데이터 작성 (상태: 작성중)
   - 관련 문서 링크 추가

3. **작성 완료**
   - 내용 검토
   - 메타데이터 업데이트 (상태: 완료)
   - Git 커밋

4. **유지보수**
   - 내용 업데이트 시 버전 증가
   - 폐기 시 상태 변경 및 아카이브

## 참고사항

- 이 규칙은 프로젝트 진행에 따라 개선될 수 있습니다
- 규칙 변경 시 이 문서를 업데이트하고 버전을 증가시킵니다
- 모든 팀원과 AI 협업 도구(Claude Code)는 이 규칙을 준수합니다
